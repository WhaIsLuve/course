# DS-15: Карточки локаций и подразделений

Этот ExecPlan отражает выполненную реализацию первой read-фичи Directory
Service. Он следует `PLANS.MD` и сохраняет решение для последующих списков,
фильтров, JOIN-ов и Dapper-фич.

## Purpose / Big Picture

Администратор может запросить одну локацию или подразделение по GUID и получить
плоский JSON для UI. Существующая запись продолжает использовать write-
репозитории и доменную модель, а чтение идёт через отдельный контракт без
операций изменения и формирует DTO непосредственно в SQL-проекции.

## Surprises & Discoveries

- В `Contracts` уже существовали `LocationResponse` и `DepartmentResponse` как
  заготовки; сохранены их публичные имена, а `LocationResponse` приведён к
  согласованной плоской форме.
- Core ранее не имел прямой ссылки на EF Core. Для асинхронного выполнения
  `IQueryable` добавлена ссылка на уже централизованно версионируемый пакет.
- В текущей конфигурации EF SQL-команды подавлялись уровнем `Warning`, поэтому
  отдельный `appsettings.Development.json` включает только command logger на
  `Information`; production-настройки не изменены.

## Decision Log

- `IReadDbContext` размещён в Core и отдаёт только `IQueryable<Location>` и
  `IQueryable<Department>`; это позволяет handler-у строить `Select`, но не
  предоставляет `Add`, `Remove`, `Update` или `SaveChanges`.
- `AppDbContext` явно реализует интерфейс и применяет `AsNoTracking()` в обоих
  свойствах; handlers не дублируют это правило.
- DTO плоские: адрес локации представлен отдельными полями, связанные
  коллекции не возвращаются.
- Автоматические query unit-тесты не добавлялись по решению пользователя;
  интеграционные тесты PostgreSQL будут реализованы позже.

## Outcomes & Retrospective

Оба endpoint-а теперь используют общий `EndpointResult<T>` и возвращают
Envelope с DTO либо not-found Error. Build завершился с 0 предупреждений и 0
ошибок, все 163 существующих unit-теста прошли. Проверка фактических HTTP
ответов и текста SQL требует доступного PostgreSQL и отложена в отдельную
интеграционную задачу.

## Context and Orientation

Проект находится в `backend/DirectoryService`. Core содержит query/command
контракты и feature-slice, Infrastructure.Postgres содержит `AppDbContext`, а
Web содержит MVC-контроллеры и Envelope results. Автоматическое сканирование в
`Core.ServiceCollectionExtensions` регистрирует новые handlers по интерфейсу
`IQueryHandler<,>`; отдельная регистрация handlers не нужна.

## Plan of Work

`IReadDbContext` добавлен в `Core/Abstractions`, а Core получил EF Core для
`SingleOrDefaultAsync`. `AppDbContext` реализует интерфейс explicit-свойствами с
`AsNoTracking`; Infrastructure регистрирует интерфейс как scoped-алиас того же
контекста. Для каждой сущности добавлены query, handler и `Select` в response
DTO. Контроллеры принимают GUID и возвращают `EndpointResult<T>`. В development
конфигурацию добавлен безопасный уровень SQL-команд без sensitive logging.

## Validation and Acceptance

- `GET /api/v1/locations/{id}` возвращает `200` с `Envelope<LocationResponse>`
  для существующей строки и `404` с `location.not.found` для отсутствующей.
- `GET /api/v1/departments/{id}` возвращает `200` с
  `Envelope<DepartmentResponse>` для существующей строки и `404` с
  `department.not.found` для отсутствующей.
- Read handlers зависят только от `IReadDbContext`; SQL-проекция выбирает поля
  DTO, а `AsNoTracking` применяется в реализации контракта.
- Build и unit-тесты выполнены; HTTP/SQL acceptance проверяется последующим
  PostgreSQL integration test suite.

## Idempotence and Recovery

Изменения аддитивны и безопасны для повторного build/test. Миграции и данные не
изменяются. При необходимости отката удаляются только новые read-файлы,
регистрация, development-конфигурация и изменения контроллеров; существующие
write-фичи и доменная схема не затрагиваются.
